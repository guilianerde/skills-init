全量安装教程workflow-run · DocNexus 文档库 · CodeGraph 代码图谱

在项目根执行一条命令，装好全部项目级 skills，同时接入 DocNexus 项目记忆和 CodeGraph 代码图谱。本页按顺序讲安装前的准备、安装器每一步做了什么、装完怎么验证，以及团队其他人怎么接入。

Node ≥ 22.13 npm git CodeGraph 约 300MB（全局一份） Windows：管理员终端

01准备

  • Node.js ≥ 22.13：DocNexus 的要求，也满足 code-graph 的 impact / entry（≥ 22.5）。版本不够时安装器会在写任何文件之前报错退出。用 node -v 查看。
  • npm 可用：DocNexus 用 npm 装进项目，CodeGraph 用 npm 全局安装。
  • 全局 npm 有写权限：CodeGraph 执行 npm i -g @colbymchenry/codegraph@1。如果平时 npm i -g 需要 sudo，先自己装好 CodeGraph，安装器发现已有 codegraph 命令就不会再装。
  • 在项目根执行：当前目录就是项目根，也可以用 --project-root 指定。
  • Windows：必须在「以管理员身份运行」的终端里执行（建目录软链接需要这个权限）。普通终端里安装器会直接停下，不做任何改动。
  • 数据库连接（可选）：有 .codex/database-query/config.json 时会自动迁移。没有或者暂时不配就加 --skip-db，以后重跑补上。
node -v        # v22.13.0 或更高
npm -v
codegraph --version   # 没装也没关系，安装器会装

03安装器做了什么

      
按执行顺序列出。前面的步骤失败会停下；DocNexus 和 CodeGraph 某一步失败时只跳过它自己，skills 照常装好。

      
    
        
  1. 检查 Node ≥ 22.13 和 npmDocNexus
    不满足就报错退出，此时还没有写任何文件。
    2. 
        
  2. 确定环境、数据库连接
    来自 --envs 或交互选择；--skip-db 时跳过数据库。
    3. 
        
  3. 安装 skills 到 .agents/skills/
    这是唯一一份完整文件，并写入安装清单 .workflow-run.json。
    4. 
        
  4. 为其他环境建软链接
    .claude/skills/<skill>、.qwen/skills/、.codebuddy/skills/ 按 skill 链接到 .agents/skills/。加 --copy 时改为各装一份。
    5. 
        
  5. 补齐 .gitignore
    只追加缺失的行：凭据文件、个人设置、/workflow-run/tmp/，加上 .codegraph/。DocNexus 的依赖和检索库由它自带的 .docnexus/.gitignore 忽略，这里不用加。
    6. 
        
  6. 安装 DocNexusDocNexus
    在业务项目根执行 npm install --prefix ./.docnexus --save-exact @rowansenne/docnexus。npm 清单、锁文件和依赖都不进宿主项目的 package.json。
    7. 
        
  7. 初始化 DocNexus 工作区DocNexus
    docnexus init --output-dir workflow-run --agent none：创建 workflow-run/docnexus/，把 DocNexus 的 skills 同步到 .docnexus/skills/。
    8. 
        
  8. 把 DocNexus 接到本项目DocNexus
    把 docnexus-recall 等 skill 软链接到所选环境的 skills 目录，并在 CLAUDE.md / AGENTS.md 写一段说明（有自己的标记，不碰手写内容）。
    9. 
        
  9. 安装 CodeGraphCodeGraph
    找不到 codegraph 命令时执行 npm i -g @colbymchenry/codegraph@1。
    10. 
        
  10. 写 MCP 配置CodeGraph
    选了 claude / codex 时执行 codegraph install --target=claude,codex --location=local --yes。doubao、qwen、workbuddy 不支持 MCP 配置，在这些环境里 skill 直接调用 codegraph CLI。
    11. 
        
  11. 建代码图谱索引CodeGraph
    codegraph init <项目根> --yes 生成 .codegraph/（本地 SQLite）。大项目需要几分钟。
    12. 
        
  12. 导入文档模板到 DocNexusDocNexus
    默认模板存为 workflow-run/docnexus/library/templates/<skill>/，已有的不覆盖。接入后文档类 skill 只从这里取模板。
    13. 
      

      
注意CodeGraph 默认上报匿名使用统计（不含代码、路径、符号名），--yes 不会询问。本工具调用 codegraph 时都带 DO_NOT_TRACK=1，但 agent 通过 MCP 使用时不受这个控制。要关闭就运行 codegraph telemetry off。

    


    

      
04装完的目录

      
以选了 claude 和 codex 为例。橙色是被 .gitignore 忽略、每人本机各一份的内容，其余都提交。


项目根/
├── .agents/skills/            # skills 唯一来源 + .workflow-run.json 安装清单
│   ├── workflow/  dev/  project-review/  code-graph/
│   ├── database-query/
│   │   └── config.json        # 数据库连接（含密码）
│   ├── md-to-wiki/wiki-config.json
│   ├── create-tech-md-doc/  create-release-md-doc/
│   └── docnexus-recall/ …     # → .docnexus/skills/ 的链接
├── .claude/
│   ├── skills/<skill>         # → ../../.agents/skills/<skill>
│   ├── settings.json          # CodeGraph：放行 codegraph_explore
│   └── CLAUDE.md              # CodeGraph 写入的说明
├── .codex/config.toml         # CodeGraph 的 Codex MCP 配置
├── .mcp.json                  # CodeGraph 的 Claude MCP 配置
├── .codegraph/                # 代码图谱索引（SQLite）
├── .docnexus/               # 项目根运行环境、skills、草稿与索引
├── workflow-run/
│   ├── docs/requirements/     # 需求产物
│   ├── docnexus/              # DocNexus 知识输出与模板
│   │   ├── CONCEPTS.md  concepts/
│   │   └── library/  records/  impacts/
│   └── tmp/
├── CLAUDE.md  AGENTS.md       # DocNexus 段落
├── .ignore                    # 让代码搜索跳过需求目录
└── .gitignore

      
.docnexus/.gitignore 随业务项目提交；.docnexus/project.json 记录输出位置。无论 workflow-run/ 是随代码提交还是独立文档仓库，依赖和检索库都不会被提交。

    


    

      
05验证

      
先跑自检。它会对比版本，检查手改或缺失的文件、软链接、项目画像、DocNexus 模板、.gitignore 凭据规则和 CodeGraph 索引。有错误时退出码是 1。

      
npx @rowansenne/workflow-run doctor --offline   # --offline 不测数据库连接

      
全量安装成功时，输出里应该有这两行：

      
    OK  DocNexus 运行环境 .docnexus/，知识输出 workflow-run/docnexus/，已接入 Agent
    OK  CodeGraph 已接入（codegraph 1.x.x，索引在 .codegraph/）

      
再确认索引和凭据都被忽略了：

      
git check-ignore -v .codegraph .agents/skills/database-query/config.json

      
在 agent 里也能看：运行 /workflow status，docnexus 和 codegraph 两项都应是 ok。

    


    

      
06第一次使用

      
    
        
  1. 重启 agent：MCP 配置要重启后才生效。Codex 只在受信任的项目里加载项目级配置，第一次打开时选择信任这个项目。
    2. 
        
  2. 填项目画像：在 agent 里运行 /workflow profile，填主分支、构建 / 测试命令、配置中心、发布平台等。画像存在 .agents/skills/workflow/profile.json，不含凭据，可以提交。
    3. 
        
  3. 试一次代码图谱：让 agent 用 code-graph 看当前分支的影响面，或者自己运行：
    4. 
      

      
node .agents/skills/code-graph/scripts/cg.mjs status
node .agents/skills/code-graph/scripts/cg.mjs impact --base main

      
接入后 skills 会自动用上这两样：

      

        
skillDocNexusCodeGraph

        
dev开始前用 docnexus-recall 查项目约定；交付时问要不要沉淀改公共方法前看入口，先跑受影响的测试，交付说明写受影响的接口、表、配置

        
project-review同上，审查报告记下库内路径「影响面」按入口归纳

        
技术 / 上线方案从知识库取模板；有值得记的内容时提议沉淀影响范围、中间件上线、回归验证参考 impact

      

      
授权任何写入 DocNexus 的操作都要你同意。没有 .codegraph/ 时 skills 不会自己建索引，只在交付或报告里注明「未使用代码图谱」。

    


    

      
07团队成员接入

      
skills、软链接、项目画像、DocNexus 知识库都随仓库提交，但这几样每人本机各一份：DocNexus 的依赖和检索库、CodeGraph 的 CLI 和索引、数据库与 wiki 凭据。所以其他人 clone 之后也要跑一次同样的命令：

      
git clone <仓库地址> && cd <项目>
npx @rowansenne/workflow-run --envs claude,codex --skip-db --with-docnexus --with-codegraph

      
    
        
  • 本次为破坏性更新：安装前强制删除旧版 DocNexus 数据和旧重复备份，不迁移、不备份；新版接入后，重跑保留项目画像、表结构和知识库里的模板。docnexus init 可以重复执行，不影响已有记忆。
    • 
        
  • Windows 上 clone 含软链接的仓库前先执行 git config --global core.symlinks true，并用管理员终端。
    • 
        
  • 需要查数据库的人去掉 --skip-db，按提示填自己的连接；这个文件已被忽略，不会提交。
    • 
        
  • 用了独立文档仓库时，安装顺序不一样，见下一节。
    • 
      

    


    

      
08独立文档仓库

      
默认情况下 workflow-run/ 随代码提交。下面两种情况适合换成团队共用的文档仓库：不想让需求产物进代码仓库，或者一个需求横跨多个服务。换了之后 workflow-run/ 本身就是文档仓库：

      
    
        
  • 代码仓库的 .gitignore 加上 /workflow-run/，不再管理它。
    • 
        
  • DocNexus 知识库也在文档仓库里，各服务共用。
    • 
        
  • 目录结构不变。两种用法下产物都在 workflow-run/docs/requirements/<需求名>/<项目名>/，同一个需求下每个服务占一个子目录。
    • 
      


team-docs/                     # 文档仓库 = 每个服务的 workflow-run/
├── docs/requirements/
│   └── 订单导出/
│       ├── order-service/     # 项目名 = profile.json 的 artifacts.project
│       └── report-service/
├── docnexus/                  # 共用知识库与模板
│   ├── .gitignore             # DocNexus 自带
│   ├── node_modules/  store/  # 每人本机一份
└── tmp/                       # 写在 .git/info/exclude，不进文档仓库

      
原地切换因为结构相同，切换只是换一个 git 仓库来跟踪 workflow-run/，文件不用挪。docs-repo 看到 workflow-run/ 里已有产物和 DocNexus 时，会原地 git init 并接上远端；里面是空的就直接克隆。所以先全量安装再切换也可以，不用讲究顺序。


      
第一次搭建（全团队只做一次）

      
先在 git 服务器上建一个空仓库，例如 team-docs，然后在第一个服务的项目根执行：

      
    
        
  1. 全量安装
    已经装过的项目跳过这一步。
    npx @rowansenne/workflow-run --envs claude,codex --skip-db --with-docnexus --with-codegraph
    2. 
        
  2. 切到文档仓库
    远端是空仓库时，workflow-run/ 里现有的内容就是文档仓库的第一批内容。安装器同时让代码仓库忽略 workflow-run/，并把项目名写进 workflow/profile.json。不加 --project 时，项目名用 git 远端的仓库名。
    npx @rowansenne/workflow-run docs-repo git@git.example.com:team/team-docs.git --project order-service
    3. 
        
  3. 提交并推送文档仓库
    依赖和检索库在业务项目根，由 .docnexus/.gitignore 忽略，tmp/ 已写进文档仓库的 .git/info/exclude，直接提交即可。
    git -C workflow-run add -A
git -C workflow-run commit -m "chore: init team docs"
git -C workflow-run push -u origin main
    4. 
        
  4. 提交代码仓库
    提交 .gitignore（新增了 /workflow-run/）和带项目名的 profile.json。如果 workflow-run/ 之前随代码提交过，先让代码仓库停止跟踪它，文件本身不受影响。
    git rm -r --cached workflow-run   # 之前提交过 workflow-run/ 时才需要
git add -A && git commit -m "chore: move workflow-run to team docs repo"
    5. 
      


      
其他服务、其他成员接入

      
文档仓库里已经有 DocNexus 了，这时要先克隆、再安装。如果反过来，安装时会在本地新建一个 DocNexus 工作区，和文档仓库里的同名文件冲突，docs-repo 会停下。

      
npx @rowansenne/workflow-run docs-repo git@git.example.com:team/team-docs.git   # 克隆到 workflow-run/
npx @rowansenne/workflow-run --envs claude,codex --skip-db --with-docnexus --with-codegraph
npx @rowansenne/workflow-run docs-repo --project report-service   # 只有新服务需要，给它起名

      
同一个服务的其他成员不用第三条命令，项目名已经随代码提交在 profile.json 里。--with-docnexus 在已有的工作区上只装本机依赖，docnexus init 可以重复执行，不影响已有记忆。


      
已经用了一段时间，要改用文档仓库

      
做法和第一次搭建一样，不用手动迁移。旧版本随代码提交时，需求目录下没有项目名这一层，先运行 upgrade，它会把这些文件迁到 <需求名>/<项目名>/ 下（被 git 跟踪的用 git mv，保留历史）：

      
npx @rowansenne/workflow-run upgrade   # 旧结构迁到 <需求名>/<项目名>/
npx @rowansenne/workflow-run docs-repo git@git.example.com:team/team-docs.git --project order-service

      
然后按「第一次搭建」的第 3、4 步提交两个仓库。如果文档仓库里已经有别的服务的内容，各服务的产物在各自的项目子目录下，不会冲突。冲突只会出在 DocNexus：两边都有知识库时，docs-repo 会退回原状，并列出冲突的文件。这时先按 DocNexus 自己的写入流程，把本项目沉淀的内容写进共用知识库，再把本地的 workflow-run/docnexus/ 挪走后重跑。


      
日常使用

      

        
场景做法

        
写完产物skill 会列出文档仓库里没提交的文件，并给出建议的提交信息。你确认后它才提交，推送另外问。查看未提交的产物：node .agents/skills/workflow/scripts/requirement.mjs pending

        
加入其他服务的需求先 git -C workflow-run pull，绑定需求时就能看到别的服务建的需求，用同一个名字绑定

        
引用产物写成「文档仓库名:路径」，例如 team-docs:docs/requirements/订单导出/order-service/review.md。在哪个服务、哪个人的克隆里都一样

        
浏览/workflow view 显示文档仓库里所有项目的需求

        
查看当前状态npx @rowansenne/workflow-run docs-repo（不带地址），显示仓库地址、引用前缀和本项目的项目名

        
改项目名npx @rowansenne/workflow-run docs-repo --project <项目名>，然后提交 profile.json

        
不想被提示提交node .agents/skills/workflow/scripts/requirement.mjs config --commit-prompt off --local，只写进个人的 profile.local.json

      

    


    

      
09升级与卸载

      
升级 workflow-run

      
npx @rowansenne/workflow-run upgrade

      
读安装清单里记录的环境，非交互升级 skills；手改过的文件先备份到 workflow-run/tmp/upgrade-backup/。已接入 DocNexus 时会刷新它的 skill 链接和说明段落，并导入新版本新增的模板（已有模板不动）。upgrade 不会升级 DocNexus 包，也不会动 CodeGraph，这两个各自升级：

      
npm install --prefix ./.docnexus --save-exact @rowansenne/docnexus@latest
npm i -g @colbymchenry/codegraph@1

      
团队改过的模板和新默认模板有差异时，用 seed-templates --diff 只读查看，再按 DocNexus 的流程手动合并。


      
卸载

      
npx @rowansenne/workflow-run uninstall   # skills 与链接；DocNexus 和 .gitignore 不动
codegraph uninit                         # 删除本项目索引
codegraph uninstall                      # 移除 agent 配置和 CLI

      
卸载时用户配置和手改过的文件先移到 workflow-run/tmp/uninstall-backup/。.docnexus/ 运行环境和 workflow-run/docnexus/ 知识输出保留，CLAUDE.md / AGENTS.md 里的 DocNexus 段落会撤掉。

    


    

      
10常见问题

      
安装结尾退出码是 1，但 skills 装好了
DocNexus 的 npm 安装或 docnexus init 失败时只跳过 DocNexus，最后以退出码 1 结束。看输出里的警告，修好网络或 npm 权限后重跑同一条命令即可。CodeGraph 失败同样只跳过它自己。

      
全局安装 CodeGraph 报权限错误
先用你平时的方式全局装好 @colbymchenry/codegraph@1（例如改用 nvm 管理的 Node），确认 codegraph --version 能运行，再重跑带 --with-codegraph 的命令。

      
codegraph init 失败或太慢
安装器会跳过建索引并提示。之后可以在项目根手动执行 codegraph init。索引建好后 agent 使用期间自动增量同步，cg.mjs 发现索引落后于工作区时也会先 codegraph sync。

      
Qwen Code 不会自动查 DocNexus
安装器不写 QWEN.md。需要自动召回时，在 QWEN.md 里引用 AGENTS.md 的 DocNexus 段落，或在 .qwen/settings.json 的 context.fileName 加入 AGENTS.md。

      
Codex 里看不到 codegraph_explore
Codex 只在受信任的项目里加载 .codex/config.toml。确认已信任这个项目并重启 Codex。

      
内网或离线安装 DocNexus
用环境变量指定安装包：DOCNEXUS_PKG=/path/to/rowansenne-docnexus-x.y.z.tgz npx @rowansenne/workflow-run --with-docnexus。PowerShell 写成 $env:DOCNEXUS_PKG="..."。

      
图谱里一个方法「没有调用方」，可以删吗
不一定。静态分析看不到 Spring 多实现的选择、AOP、反射和配置驱动的路由，「没有调用方」不等于没人用。
