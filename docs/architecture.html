为什么做

同一个代理，换个人用、换个模型，结果就不一样

代理很会写代码，但它不知道你们的主分支叫什么、构建命令是什么、哪些改动上线前要列配置清单，也不知道团队上次在哪里踩过坑。每个人各写各的提示词，产出的格式和质量就各不相同。workflow-run 把这些放进项目里，所有人、所有代理读的是同一份。

每人一套提示词，交付格式靠自觉
dev、审查、文档各有固定流程和模板，产物落在同一个需求目录
代理自己猜构建命令、凭类名猜表结构
项目画像记录构建与测试命令；表结构以只读查库的结果为准
改完说「测试通过」，没人知道跑没跑
每条验收标准对应到测试或操作；没验证的写明原因
整体架构

五层：代理只碰最上面两层，规则和脚本在下面托底

skill 只写流程和判断，所有能确定的事（找模板、定产物路径、识别涉及的表、文档自检）都交给脚本。脚本结果是固定的，模型强弱只影响判断，不影响格式。

安装器 bin/

和运行流程分开：负责安装、升级、卸载、自检，不参与开发。

每个 skill 的依赖、模板、知识库分类都写在自己的 skill.json 里，安装器、脚本、测试都从这一份读。

升级只换 skills 文件；项目画像、数据库和 wiki 配置保留不动，手改过的文件先备份。

doctor 检查链接、画像、凭据是否被忽略、数据库能否只读连上。

主线：dev

一个需求从描述到交付，人只在关键处拍板

/dev <需求> 或 /dev --bug <现象> 进入。事实代理自己查（代码、表结构、PRD、历史沉淀），决定交给人（业务规则、取舍、范围）。

  1. Step 0
    前置检查
    读画像，问清工作区里已有的改动归谁，跑一次基线
  2. F1
    理解需求
    拉 PRD，召回以往的约定和坑，列初版验收标准
  3. F2
    现状调研
    沿调用链读代码，只读查实际表结构
  4. F3
    需求澄清
    分轮提问，每题带推荐答案；M / L 确认理解一致
  5. F4
    方案
    按规模分级；M / L 确认方案后才写代码
  6. F5
    实现
    贴合现有写法，不顺手重构；SQL 只写脚本不执行
  7. F6
    验证
    先相关测试再全量；验收项逐条对应到证据
  8. F7
    自审
    用 project-review 审本次改动，CRITICAL / HIGH 必须修
  9. F8
    交付
    交付说明落盘；提交、PR、沉淀都先问
需要人确认的节点缺陷修复走 B1 收集现象 → B2 复现 → B3 定位根因 → B4 最小修复 → B5 自审交付
S · 快速通道

≤3 个文件，不碰接口、表、配置、权限、资金。编译、测试、自审照做，在对话里交付，不落盘。

M

改接口、配置项、少量字段，或涉及权限、资金。先确认需求理解，再确认简要方案。

L

新模块、跨服务、数据迁移。方案写成文档落盘，确认后再写代码，之后可生成正式技术方案。

设计取舍

几条贯穿所有 skill 的约定

项目事实只写一处

主分支、构建和测试命令、配置中心、发布平台都在 workflow/profile.json。模板里不写死任何公司或项目的约定，换个项目只改画像。

能用脚本就不靠模型

模板该取哪份、产物写到哪、改动涉及哪些表、文档缺了哪节，都由脚本给出 JSON 结果。命令在 bash、zsh、PowerShell 里写法一样。

增强能力缺了就降级

没装 CodeGraph 就用 grep，查不了库就读 DDL 并注明「未与实际库核对」，没接 wiki 就请用户贴 PRD。任何一项不可用都不会卡住流程。

不可逆的事一律先问

不写库、不 commit、不 push、不装依赖、不写知识库，除非用户在本次对话里明确同意。SQL 只写成脚本交给人。

一份文件，五个环境

skills 只在 .agents/skills/ 装一份，其他环境用相对软链接指过去。改模板、填配置只改一处，整个目录可以提交给团队。

结论要有出处

关于现有代码的结论指向真实文件和行号；审查发现要写出触发条件，严重级别的发现交给独立的子代理复核，减少误报。

8 个 skill

按需安装，依赖自动带上

--skills dev 会一起装上它必需的 workflow 和 project-review；可选的协作 skill 没装时，对应步骤跳过。

skill做什么依赖
workflow入口：按请求路由到对应 skill；维护项目画像；status 检查各能力是否可用无
dev功能开发与缺陷修复，从需求澄清到交付说明workflow project-review
project-review审分支或未提交改动：14 维度清单、影响面、发现复核、复审对比workflow
code-graph基于 CodeGraph：改动影响到的接口、MQ 消费者、定时任务、测试、SQL 和表workflow
database-query会话级只读查询，拦截写语句、自动 LIMIT、敏感字段脱敏独立
create-tech-md-doc从分支 diff 按团队模板生成技术方案workflow
create-release-md-doc从分支 diff 生成上线方案，自动引用同分支的技术方案和交付说明workflow
md-to-wiki把 md 转成 Confluence 格式并发布；未配置时不启动独立
产物与知识

一个需求的所有文档放在一起，好的经验会回到下一次开发

workflow-run/docs/requirements/
└── 订单导出/                # 需求名由你定
    └── order-service/       # 项目名，跨服务各占一层
        ├── meta.json        # 分支、版本、wiki、沉淀记录
        ├── plan.md          # 开发方案（L）
        ├── delivery.md      # 交付说明
        ├── review.md        # 审查报告
        ├── tech-doc.md      # 技术方案
        └── release-doc.md   # 上线方案

可以随代码提交，也可以把 workflow-run/ 整个换成团队的独立文档仓库，多个服务共用，目录结构不变。npx @rowansenne/workflow-run view 生成本地页面按需求浏览。

1
开工前召回

dev 和审查先查 DocNexus 里以往的开发约定、技术方案和反复出现的审查问题。

2
过程中引用

用上的知识在产物里写明出处 docnexus/library/<path>。

3
交付时沉淀

每次交付都问要不要沉淀：已确认的决定、新约定、缺陷根因。同主题的更新原文，不重复新建。

4
下次被召回

审查沉淀的问题模式，会在下一次 dev 开工时被列出来。

写入知识库每次都要你同意；没接入 DocNexus 时不提问，也不提示安装。
持续改进

skill 自己也按数据迭代

dev 和 project-review 每跑完一次，静默记一行过程数据到 workflow-run/feedback/<用户>.jsonl：提问了几轮、用户纠正过几次理解、跳过了哪些步骤、哪条规则读不懂或做不到。只记过程，不记代码和业务名词，也不额外打扰用户。

团队用两三周后，npx @rowansenne/workflow-run feedback 按 skill 和章节汇总，据此精简或修正规则、发新版本；各项目升级时清掉旧版本的记录，从新版本重新收集。结果类数据（审查发现、修复率、沉淀率）则由 report 命令从产物里统计。
