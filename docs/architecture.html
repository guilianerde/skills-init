为什么做

同一个代理，换个人用、换个模型，结果就不一样

代理很会写代码，但它不知道你们的主分支叫什么、构建命令是什么、哪些改动上线前要列配置清单，也不知道团队上次在哪里踩过坑。每个人各写各的提示词，产出的格式和质量就各不相同。workflow-run 把这些放进项目里，所有人、所有代理读的是同一份。

每人一套提示词，交付格式靠自觉
dev、审查、文档各有固定流程和模板，产物落在同一个需求目录
代理自己猜构建命令、凭类名猜表结构
项目画像记录构建与测试命令；表结构以只读查库的结果为准
改完说「测试通过」，没人知道跑没跑
每条验收标准对应到测试或操作；没验证的写明原因
整体架构

安装分发独立，流程、命令、共享核心与能力工具协作

宿主代理读取 skill 规则、判断任务并调用脚本；workflow-run 不提供常驻的 Agent 调度服务。工作流命令将共享的路径、数据模型、读取和状态写入交给 workflow/lib，数据库、wiki、Nacos 等能力的执行留在各自目录。

下图按职责分区，每次请求只经过需要的部分。dev 仅在实际调用 /dev / $dev、点选 skill 或明确要求完整开发工作流时启动；普通分析、修改、测试、提交和推送直接处理。nacos-config 可独立查询，也可在开发或审查中提供配置证据。

安装器 bin/

和运行流程分开：负责安装、升级、卸载、自检，不参与开发。

bin/skills.mjs 从各目录的 skill.json 自动发现 skills，读取依赖、用户文件、模板和知识分类；package.json.files 控制 npm 包内容。workflow/lib 随 workflow skill 安装。

共享核心不反向依赖命令脚本、纯模型不做 I/O——这条边界写进了测试，违反会直接跑挂。安装器自己的环境探测也用 lib/project，不另写一份。

升级只换分发文件；项目画像、数据库、wiki 和 Nacos 本机配置保留不动，手改过的文件先备份。默认单一来源 + 相对软链接，也支持 --copy。

DocNexus 在安装环节必装，哪怕只选 Nacos；Nacos 读取脚本没有 workflow / DocNexus 运行依赖。DocNexus 自带 skills 不计入本包的 9 个。

npx @rowansenne/workflow-run doctor 检查链接、画像、凭据是否被忽略、数据库能否只读连上。

调用与状态

完整流程记录证据，独立查询按需读取

开发 / 审查路径

宿主代理 → dev / project-review
  → workflow/scripts 命令
  → workflow/lib：门禁、代码证据、状态
  → workflow-run：Markdown + meta.json
  ↳ 按需调用图谱、数据库、wiki、Nacos

完整 dev 的方案批准绑定正文版本，验证和审查绑定执行前代码快照，交付选择绑定本轮报告。artifact 收尾登记待办后发布、归档、更新索引；中断可 resume 或 abort。S 快速通道不绑定需求、不建运行、不落盘。

Nacos 独立路径

宿主代理 → nacos-config
  → inspect：仅查看本地配置候选
  → 明确环境、Namespace / Group / Data ID
  → get：鉴权 + 只读 HTTP 获取
  → 脱敏属性 + 来源、读取时间、摘要

不创建需求、运行或原文缓存，不改数据库连接。仅配置 GET 与登录 POST；多个环境不猜选。结果是单个配置快照，不代表 Spring 合并、灰度与刷新后的运行时最终值。

meta.json 保存绑定、版本索引、runs 与收尾待办，Markdown 保存正文和发布 / 沉淀引用。view / report 只读取快照；文件存在不等于运行完成。lib 不反向依赖 scripts，纯模型不做 I/O。实现细节见 内部模块边界。
主线：dev

一个需求从描述到交付，人只在关键处拍板

用户实际调用 /dev <需求>、/dev --bug <现象>、$dev，或明确要求 dev / 完整开发工作流后才进入。事实代理自己查（代码、表结构、远程配置、PRD、历史沉淀），决定交给人（业务规则、取舍、范围）。

Codex 元数据关闭隐式调用；其他环境也由入口规则和项目说明约束。讨论命令、发现旧运行、要求分析或提交代码都不启动新流程。已授权任务可按保存阶段续接，当前独立操作不重做前置步骤或自行推进阶段。

  1. Step 0
    前置检查
    读画像，先确定工作分支，再问清需求名（给不出就不开始）与工作区里已有的改动归谁，跑一次基线
  2. F1
    理解需求
    拉 PRD，召回以往的约定和坑，列初版验收标准
  3. F2
    业务核对与调研
    先落业务场景清单，与产品逐轮核对；明确后结合场景调研代码与数据
    clarification.md
  4. F3
    需求澄清
    基于已确认场景澄清可行性、接口兼容、数据与权限等技术约束；确认理解一致后收尾需求文档
    requirement.md
  5. F4
    方案
    需求明确后引用需求版本，写实现设计、实施和验证计划（S / M 简版）；M / L 确认方案后实现
    plan.md
  6. F5
    实现
    贴合现有写法，不顺手重构；SQL 只写脚本不执行
  7. F6
    验证
    先相关测试再全量；完整流程绑定执行前代码快照，验收项逐条对应到证据
  8. F7
    审查
    完整流程自动生成交接材料，优先独立子 agent 审查；返回草稿与结构化结果，由主 agent 收尾 review.md，再等用户选择修复或交付
    review.md
  9. F8
    交付
    用户选择交付后才生成交付说明；提交、PR 先问，沉淀有值得记的内容才问
    delivery.md
需要人确认的节点正式产物落盘：F2 clarification.md（业务核对）→ F3 requirement.md → F4 plan.md → F7 review.md → F8 delivery.md（选择交付后）；S 快速通道不落任何产物缺陷修复走 B1 收集现象 → B2 复现 → B3 定位根因并生成 requirement.md → B4 追加 plan.md → B5 审查与交付（review.md / delivery.md）
F3 前先核对业务场景，再澄清技术约束

输出待确认清单 → 用户与产品核对、完善 PRD → 带回答复或新版 PRD → 更新原清单并追加新问题。每轮保留 Q 编号与已确认项，汇总「已确认 / 仍待确认 / 本轮新增」和 PRD 调整建议；仍有未定业务项就留在 F2，继续这个循环。

业务场景明确后，完成 F2 现状调研，再进入 F3 核对系统能力、接口、数据、兼容性等技术约束；技术限制改变业务场景时回 F2 找产品确认。业务与技术均明确后，收尾 requirement.md、进入 F4 写实现方案。没有业务待确认项且用户未要求清单时可省清单，沿用快速通道判定。

清单按 clarification-template.md 生成，经 finalize 发布到同一需求目录；每轮归档旧版，等待时保存 waiting_user，新会话恢复同一运行继续。清单发布不代表 F2 调研或 F3 技术澄清已完成；清单关注角色、操作场景、业务规则、范围和验收。
S · 快速通道

≤3 个文件，不碰接口、表、配置、权限、资金，无 F2 / F3 已确认的业务决定，本次未发布正式清单且未创建完整运行。已有清单或运行继续完整流程；符合资格时走不走由用户选：同意则编译、测试照常，审查在当前会话做；不绑定需求、不落产物文件（连方案也不写），一次对话交付并注明「未询问」。

M

改接口、配置项、少量字段，或涉及权限、资金。先确认需求理解，再确认落盘的简要方案。

L

新模块、跨服务、数据迁移。写完整方案文档落盘，确认后再写代码，之后可生成正式技术方案。

设计取舍

几条贯穿所有 skill 的约定

项目事实只写一处

主分支、构建和测试命令、配置中心、发布平台、开发环境配置（toolchain：JDK / Maven / Node 的位置）都在 workflow/profile.json。模板里不写死任何公司或项目的约定，换个项目只改画像；个人机器不同的部分写进不提交的 profile.local.json 覆盖。

能用脚本就不靠模型

模板该取哪份、产物写到哪、改动涉及哪些表、文档缺了哪节，都由脚本给出 JSON 结果。命令在 bash、zsh、PowerShell 里写法一样。

开工统一选择能力

工作流开工快照检查必装 DocNexus，并选择 CodeGraph、数据库和 wiki 通道。Nacos 由独立 skill 按需读取，尚未纳入集中状态探测；config_center: nacos 只说明项目类型，不代表连接已验证。

按任务授权执行写操作

提交、推送、发布 wiki、写知识库按流程取得授权；数据库默认只读，可写连接也须明确同意后执行写语句。Nacos skill 仅提供读取；安装器按安装请求接入所需依赖。

一份文件，五个环境

默认在 .agents/skills/ 装一份，其他环境逐 skill 建相对链接；--copy 可改为各装一份。规则可共享，连接和本机依赖不提交；生效模板保存在 DocNexus。

结论要有出处

关于现有代码的结论指向真实文件和行号；审查发现要写出触发条件，严重级别的发现交给独立的子代理复核，减少误报。

9 个 skill

按需安装，依赖自动带上

--skills dev 会一起装上它必需的 workflow 和 project-review；可选协作没装时跳过对应增强。--skills nacos-config 无其他 skill 依赖；安装器仍接入必装 DocNexus。

常用命令

日常就两类输入：代理里说需求，终端里管安装

开发、审查、出文档在装好 skills 的代理会话里完成；安装、升级、自检在项目根的终端执行，命令前缀统一是 npx @rowansenne/workflow-run，下表写全。

代理里输入做什么
/dev <需求描述>功能开发全流程：确定工作分支 → 定需求名 → F2 业务场景清单与产品核对（多轮更新）→ F3 技术澄清 → 需求明确 → 方案 → 实现 → 测试 → 独立子 agent 审查与报告（无则当前会话自查）→ 用户选择修复或交付（完整交付才生成交付说明）
/dev --bug <现象>缺陷修复全流程：复现 → 定位根因 → 最小修复 → 验证 → 审查报告 → 用户选择修复或交付
/workflow按明确请求路由独立能力；dev 须有显式流程授权。普通修改或提交不进入 dev；不带请求时输出能力地图和状态
/workflow profile填写或更新项目画像（主分支、构建测试命令、toolchain）
/workflow status开工快照：DocNexus 必装门槛、CodeGraph 通道、数据库与 wiki 配置
读取测试环境 Nacos 的 order.yaml，查看 order.timeout进入 nacos-config：定位本地连接，选择环境和 Data ID，再只读获取脱敏结果
/workflow template <模板> [怎么改]修改或创建文档模板：clarification、requirement、tech、release、plan、delivery、review、checklist
/create-tech-md-doc <dev分支> <主分支>从分支 diff 按团队模板生成技术方案
/create-release-md-doc <dev分支> <主分支>生成上线方案，自动引用同分支的技术方案和交付说明
/workflow report效果报告：审查发现与修复率、需求澄清、DocNexus 沉淀与复用
/workflow view按需求浏览全部产物的本地页面（加 --open 直接打开）
/md-to-wiki <md> [pageId]发布到 Confluence；发布过的文档省略 pageId 直接更新

project-review 和 database-query 没有斜杠命令：直接说「审一下这次改动」「查一下 order 表有哪些索引」就会触发。

终端里执行（项目根）做什么
npx @rowansenne/workflow-run init --with-docnexus --with-codegraph首次安装 / 重装；--skills dev 只装子集，--copy 不建软链接
npx @rowansenne/workflow-run upgrade升级到当前版本：用户配置保留，手改过的文件先备份
npx @rowansenne/workflow-run doctor自检：版本、软链接、项目画像、DocNexus 模板、数据库连通、.gitignore
npx @rowansenne/workflow-run seed-templates把自带的文档模板导入 DocNexus（已有的不覆盖）
npx @rowansenne/workflow-run view --open生成并打开项目文档视图（同 /workflow view）
npx @rowansenne/workflow-run docnexus view打开 DocNexus 知识库的本地只读浏览页面（前台常驻，Ctrl+C 停止）
npx @rowansenne/workflow-run report --since 2026-10-01效果报告（同 /workflow report），只读统计产物
npx @rowansenne/workflow-run feedback --json运行反馈汇总：提问轮数、跳过的步骤、读不懂的规则，精简 skill 的依据
npx @rowansenne/workflow-run docs-repo <仓库地址>改用团队独立文档仓库；不带地址显示当前状态
npx @rowansenne/workflow-run uninstall按安装清单卸载，用户配置备份到 workflow-run/tmp/

skill 内部还有一批脚本命令（resolve.mjs、requirement.mjs、review-scope.mjs、template.mjs、locate.mjs、tables.mjs、knowledge.mjs 等），由各流程自动调用，不用记。

连接配置

各能力维护连接，配置检查与远端验证分开

默认在 .agents/skills/ 维护连接，其他环境通过相对软链接复用；--copy 时各份独立。数据库、wiki 与可选 Nacos 本机连接均已加入 .gitignore，重装保留。配置存在只说明可以尝试连接，网络与鉴权仍由实际请求验证。

      "database": "app",
      "user": "app_ro",
      "password_env": "APP_DEV_DB_PASSWORD",
      "readonly": true
    }
  },
  "mask_columns": ["id_card", "phone"]
}
  • 只读是默认：readonly 为 true 或缺省都按只读处理，写语句在会话层直接拦截；只有显式 "readonly": false 的连接才允许写，而且要你点名用那个连接。
  • 密码不进对话：按 password_env 指向的环境变量 → DB_PASSWORD → password 字段的顺序取，推荐用环境变量。
  • mask_columns（顶层或单连接，正则数组）追加脱敏列；手机号、证件号、银行卡等默认已打码。
  • npx @rowansenne/workflow-run doctor 会试连一次验证配置（--offline 跳过连通性测试）。

wiki 连接 · md-to-wiki/wiki-config.json

安装后默认 enabled: false，不配置就不启动。按环境分两种情况：

没装 wiki MCP —— 填 enabled: true + base_url + api_token（Confluence 的个人访问令牌）和 username，发布与 PRD 拉取走 REST 通道：

{
  "enabled": true,
  "wiki": {
    "base_url": "https://wiki.example.com",
    "username": "me@example.com",
    "api_token": "‹Confluence PAT›",
    "remote_url": ""
  }
}
  • 已装 wiki MCP（如 Claude Code 里配了 wiki-mcp，工具名形如 mcp__wiki-mcp__get_page）：skill 自动优先走 MCP 通道，REST 字段可以不填；mcp_server 默认 wiki-mcp，remote_url 可选记录远程 MCP 地址。
  • 两种都配了：有 MCP 工具就用 MCP，没有再走 REST。
wiki 未配置时 md-to-wiki 直接不启动；技术 / 上线方案的 --prd 增强自动回退纯 diff 流程，文档生成主流程不受影响。dev 拉 PRD 用同一套判定。

Nacos · 优先复用 application / bootstrap

不强制填写第二份连接。inspect 列出本地候选，明确环境后，get 从所选文件解析 Nacos 参数与占位符。也可自行创建 nacos-config/config.json，用 --conn test 选择命名连接，密码 / token 仅通过环境变量引用。详情见 连接格式与协议。

node .agents/skills/nacos-config/scripts/config.mjs inspect
node .agents/skills/nacos-config/scripts/config.mjs get --file src/main/resources/bootstrap.yml --file src/main/resources/application-test.yml --data-id order-test.yaml --key order.timeout

支持 JSON / YAML / properties；首次解析 YAML 若缺依赖，在该 skill 目录运行 npm 安装。默认使用 Nacos 1.x / 2.x 的兼容 API，也可显式选择 2.x API 或 3.x Client API。/workflow status 与 doctor 均不测试 Nacos 远端连通性；doctor 会检查本机连接文件的忽略规则。

持续改进

skill 自己也按数据迭代

dev 和 project-review 每跑完一次，静默记一行过程数据到 workflow-run/feedback/<用户>.jsonl：提问了几轮、用户纠正过几次理解、跳过了哪些步骤、哪条规则读不懂或做不到。只记过程，不记代码和业务名词，也不额外打扰用户。

团队用两三周后，npx @rowansenne/workflow-run feedback 按 skill 和章节汇总，据此精简或修正规则、发新版本；各项目升级时清掉旧版本的记录，从新版本重新收集。结果类数据（审查发现、修复率、沉淀率）则由 npx @rowansenne/workflow-run report 命令从产物里统计。
