# 需求调研与方案

功能开发进入 F1～F4 时读取对应小节；缺陷修复在 B4 判定规模与快速通道前读取 F4。

### F1 — 理解需求

- 需求来源是 PRD pageId/URL → 按 `prd-fetch.md` 拉取并提炼。
- 先运行 `node <skills>/workflow/scripts/knowledge.mjs dev --match <模块名 / 业务名词> --query "<一句话需求>"`，看以往开发沉淀、技术方案和反复出现的审查问题里有没有相关的（`--query` 在这些分类内按正文 recall）。引用 `workflow-run/docnexus/library/<path>`（见 `<skills>/workflow/references/docnexus.md`「按分类参考知识库」）。
- 先在心里列出初版 **需求要点 + 验收标准**（可验证的行为，而不是实现手段）和还没定的决定，带进 F2 查事实、F3 澄清。

### F2 — 现状调研

- 从入口（Controller / Handler / CLI / 页面）沿调用链读到持久层，理清数据流；不凭文件名猜内容。按本轮 CodeGraph 通道先用 `codegraph_explore` / `codegraph explore "<问题>"` 一次拿到链路上的源码和调用路径，再按需补读；Spring 注入、MyBatis XML、MQ、配置 key 这些图谱看不到的照常 grep（见 `<skills>/workflow/references/codegraph.md`）。
- 找到同类功能的既有实现，作为风格与结构的参照（命名、分层、异常、日志、事务、DTO 转换方式）。
- 涉及数据库 → 按 `<skills>/workflow/references/tables.md` 先确定涉及哪些表（`tables.mjs --files <读到的实体 / Mapper>`），按本轮数据库通道用 `query.mjs --schema --tables <表> --indexes` 只读拉取实际字段、索引与行数；方案里的字段名、类型、索引和 DDL 以查到的为准，不凭实体类推测。

### F3 — 需求澄清

按 `clarify.md` 分轮提问：把需求拆成决策树（行为、边界、异常、兼容、权限、数据、范围），**事实自己查**（代码、表结构、PRD、DocNexus），**决定交给用户**；每轮把现在就能问的问题一次问完，编号并给出推荐答案和依据，等用户回答后再问下一轮，直到没有被默默假设的决定。

| 情况 | 做法 |
|---|---|
| S 规模且 F2 后没有未定的决定 | 跳过需求澄清提问，写明本次的理解和假设；F3 收尾按 F4 标准判定规模并告知用户 |
| 只有一两个小决定 | 问一轮即可 |
| M / L 规模，或用户说「拷问一下 / grill me / 先把需求问清楚」 | 按轮问到前沿为空，输出需求要点、验收标准、不在本次范围、已确认的决定，**等用户确认理解一致**再进 F4 |

不要边写代码边问：实现中才发现的新决定，停下来按同样格式问，再继续。

**澄清后的首个产物**：先按下文 F4 标准判定规模并决定是否走快速通道，已有答复直接复用，不再问一次。完整流程在此绑定需求、创建 feature 运行（stage F3，仅补记 Step0、F1、F2），用 `resolve.mjs template dev requirement-template.md` 取生效模板，将目标、范围、不做什么、验收标准（AC 编号）、已确认决定与剩余问题写到独立草稿。通过 `artifact.mjs finalize --kind requirement` 收尾为 `requirement.md` 并将 F3 标 completed，再进入 F4。M / L 仍按上表先确认理解一致，不新增一轮重复确认；阻止实现的业务决定未明确时停在 F3。

`requirement.md` 是需求事实来源，`context` 只保存续接摘要，不单独维护另一套验收。方案、验证和审查引用该文档的版本与 AC 编号。需求变化时回 F3 更新、重新收尾，再根据新版本更新方案并重新确认 / 验证；仅调整实现方案不改需求文档。历史需求不会自动从旧 plan.md 拆出正文；恢复旧开发运行需要先核实并补齐需求文档。

### F4 — 方案（落盘只看是否快速通道，写法按规模）

| 规模 | 判定 | 做法 |
|---|---|---|
| **S** | ≤3 个文件，无接口签名 / 表结构 / 配置项变更，不涉及权限 / 资金 | 符合快速通道条件时先问用户是否走：同意则不落盘、直接在对话里开始实现；不同意或未明确同意则落简版方案（要做什么、改哪些文件、怎么验证，一两行）再实现 |
| **M** | 新增或修改接口、配置项、少量表字段 | 方案落盘简版（要点 + 步骤），**等用户确认后再写代码** |
| **L** | 新模块、跨服务、表结构较大变更、数据迁移 | 按方案模板写完整方案文档落盘（见 Artifact Location），用户确认后再写代码；完成后建议用 `create-tech-md-doc` 生成正式技术方案 |

规模拿不准时按大一级处理。涉及权限（鉴权、角色、数据可见范围）或资金（金额计算、扣款、退款、对账）的改动，文件再少也至少按 M：需求理解（F3）和方案都要用户确认。

**规模判定（S / M / L 都必做，不再询问用户）**：规模由你按上表判定，向用户说明判定的规模与依据（预计改动文件 / 模块、接口 / 数据 / 配置变化及风险）即可，**不询问、不等确认**，直接按该规模推进后续流程；用户主动提出不同意见时，按用户说的规模继续。用户调整范围或实现中发现规模变化时，说明变化依据，按新规模继续。规模判定属于流程选择，不算 F3 的业务决定，不影响 S 规模快速通道资格。

**需求绑定与方案依据**：完整流程已在 F3 收尾前绑定并生成 requirement.md，本步直接沿用；方案头写需求文档的 cite 与版本，需求目标、范围和业务决定不复制到方案中维护。方案只解释如何实现，并用 AC 编号关联验证计划。S 快速通道不绑定。

**S 规模快速通道（问用户）**：判定为 S 规模，且改动**不涉及**配置项、SQL / DDL、对外接口（HTTP 接口签名、MQ 消息体、对外 DTO）、表结构、权限、资金，也没有 F3 中确认过的业务决定时，**明确询问用户是否走快速通道**：说明走快速通道时 F5～F6 照常（编译、测试都不省），审查按 F7 的快速通道说明在当前会话做，但**不绑定需求、不落任何产物文件**——方案、`review.md`、交付说明都不写（运行反馈仍照常记一行），F8 在对话里一次交付并注明 DocNexus「未询问」。**问完等本轮答复再继续：明确同意才走快速通道；拒绝或答复没有明确同意，就按完整流程落盘交付（F3 需求 → F4 方案 → F7 审查 → F8 交付）。** 实现中一旦碰到上面任何一项、改动超过 3 个文件，或用户要求落盘 → 退出快速通道：先停下后续实现，重新评估并说明规模，按 Artifact Location 绑定需求，先回 F3（缺陷回 B3）补写并 finalize requirement.md，再到 F4 / B4 补方案；M / L 等用户确认方案后再继续，S 按简版方案推进。之后回 F5 完成实现、F6 验证、F7 审查并生成 `review.md`，交报告后等待用户选择交付，不从绑定直接跳到审查或交付。快速通道只省落盘与沉淀询问，不省审查。

**方案一律落盘（走快速通道除外）**：S / M / L 都写方案文档，规模只决定详细程度和确认方式。方案模板：在项目根运行 `node <skills>/workflow/scripts/resolve.mjs template dev plan-template.md`，读输出的 `path`。方案草稿通过 `<skills>/workflow/references/execution.md` 的 `artifact.mjs finalize --kind plan` 自检、归档并登记 F4；M / L 等用户确认并 save approval 后再进入 F5，S 无需 approval（方案按简版写）。S 先按上面的快速通道问一次：同意则不写方案，不同意或未明确同意才落盘。
