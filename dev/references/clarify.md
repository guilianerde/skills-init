# 需求澄清：分轮提问

<!-- 做法借鉴 grill-me（Matt Pocock 的 grill-me / grilling skills：https://github.com/mattpocock/skills），按开发需求的场景改写 -->

目标：动手前和用户对「要做成什么样」达成一致，不留下被默默假设的决定。返工最贵的情况是：代码写完了才发现边界、异常或兼容性理解错了。

## 决策树

把需求拆成一棵决策树：每个决定下面挂着依赖它的决定。开发需求常见的分支：

| 分支 | 典型问题 |
|---|---|
| 行为 | 正常路径的输入、输出、状态变化；谁会调用 |
| 边界 | 空值、空列表、上下限、重复请求、时区、精度 |
| 异常 | 下游失败、超时、数据不一致时返回什么、要不要重试 / 告警 |
| 兼容 | 老客户端 / 老数据 / 已有调用方受不受影响；要不要开关灰度 |
| 权限 | 谁能调、能看到谁的数据 |
| 数据 | 要不要改表、迁移历史数据、保留多久 |
| 范围 | 哪些明确不做、哪些留到下一期 |

不是每个需求都有所有分支；只展开这个需求真正有的。

## 事实自己查，决定交给用户

- **事实**：代码现在怎么做、表里有什么字段、配置怎么设、PRD / DocNexus 里写过什么、git 历史里为什么这样改——都自己查（读代码、`tables.mjs` 定位表、`database-query` 只读查表结构与索引（见 `<skills>/workflow/references/tables.md`）、`knowledge.mjs`、`git log -L`），不要问用户。
- **决定**：业务规则、取舍、范围、上线方式——交给用户，每个问题都等用户回答，不要替用户回答。
- 命名、分层、异常写法这类实现细节按项目既有写法自己定，不拿来问用户。

## 分轮提问

**前沿**：前置决定都已经定下、现在就能问的问题。每一轮把整个前沿一次问完，编号，每个问题都给出你的**推荐答案**和依据（引用查到的代码 / 文档）；然后等用户回答再进入下一轮。依赖本轮另一个问题答案的问题，留到下一轮。

```
❓ **Q1 · <问题标题>**：<问题；有选项时列出选项>

➡️ 推荐：<你的推荐>。依据：<代码位置 / 文档 / 理由>

---

❓ **Q2 · <问题标题>**：…

➡️ 推荐：…
```

- 每轮问题控制在 7 个以内；超过时先问对设计影响最大的。
- 用户回答「按推荐来」→ 本轮所有推荐都算用户确认的决定。
- 用户的回答改变了决策树（例如决定不做某个分支）→ 重新计算前沿，砍掉不再相关的问题。
- 还在查的事实只挡住依赖它的问题；其余前沿问题照常问。

## 什么时候结束

前沿为空时结束：决策树每个分支都走到了，没有被默默假设的决定。这时输出：

- **需求要点**、**验收标准**（可验证的行为）、**不在本次范围**
- **已确认的决定**：每条一句话，标注是用户决定还是按推荐采纳

M / L 规模等用户确认「理解一致」后，按 planning.md 的 F3 收尾先生成独立 requirement.md，再进入方案；这些决定保存在需求文档，plan.md 只引用需求路径与版本，交付说明按需汇总。值得长期记住的业务规则与取舍在交付时作为 DocNexus 沉淀候选。
