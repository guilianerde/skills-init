# 业务场景清单与技术澄清

<!-- 做法借鉴 grill-me（Matt Pocock 的 grill-me / grilling skills：https://github.com/mattpocock/skills），按开发需求的场景改写 -->

先与产品确认「用户在什么场景下要得到什么结果」，再结合现有系统澄清技术约束与影响。功能开发在 F2 输出业务清单，F3 做技术澄清；缺陷修复在 B3 内按先业务、后技术的顺序处理。

## 事实自己查，决定交给用户

- **事实**：PRD / DocNexus 已有规则、代码现状、接口、表结构和配置，自己查证，不拿能查到的事实反问用户；数据库按 `<skills>/workflow/references/tables.md` 只读核对。
- **决定**：产品规则、范围，以及会改变业务结果的技术取舍，给用户推荐答案和依据，等实际答复，不代替确认。
- 命名、分层和项目已有的实现惯例自己定；详细实现设计留在 F4。

## F2 — 先落业务场景待确认清单

F1 形成初版需求理解后，在 F2、进入 F3 之前先输出清单，不必等技术问题全部查完。有未定业务场景或用户需要拿去与产品核对时，按 F4 标准初判规模并说明依据，选择完整流程，在首次落盘前 bind、start（stage F2，仅补记 Step0、F1，不能提前标 F2 completed）。读取 `resolve.mjs template dev clarification-template.md` 的生效模板，先写 tmp 草稿，再用 `artifact.mjs finalize --kind clarification` 发布到需求目录的 `clarification.md`，给用户文件链接。

清单聚焦产品能回答的问题：

| 内容 | 核对重点 |
|---|---|
| 角色与目标 | 谁在用，要解决什么问题 |
| 正常场景 | 什么前置条件，做什么操作，预期看到什么结果 |
| 业务边界与异常 | 重复操作、取消、失败、无数据时业务上怎么办 |
| 业务规则 | 哪些人可做、哪些数据可见、状态如何变化 |
| 范围与验收 | 本次做什么、不做什么，怎样算完成 |

接口字段、表结构、框架选择、重试机制等技术问题留到 F3 查证或 F4 设计；如果技术限制需要产品取舍，转换为对业务场景的影响再写入清单。只展开与本需求有关的场景，不穷举极端情况。

清单是正式流程产物，与 requirement.md、plan.md 同目录，纳入版本归档、文档视图和统计。发布清单不代表 F2 调研完成；等待产品反馈时保持 F2 in_progress，保存 status: waiting_user、waiting_for，以及 context 中的清单引用与待反馈事项。没有未定业务决定且用户未要求清单时，对话写「业务待确认项：无」，不额外落盘，后续沿用快速通道判定。

## 每轮怎样更新清单

- 同一份清单维护最新状态：场景用 SC-1、SC-2…，问题用 Q1、Q2…；编号稳定，新场景 / 问题接着编号，保留已确认项，不整份重排。
- 每项写清场景、问题、业务影响、推荐答案与依据、产品 / 用户答复、状态；推荐只是建议，没有实际答复不能标已确认。
- 依赖前置答案的问题也记录，注明「待 Qx 确认后讨论」。每轮突出当前能确认的问题，控制在 7 个以内；用户说「按推荐来」只确认本轮已经给出的推荐。
- 用户带回答复或新版 PRD 后，恢复同一运行，从正式清单复制 tmp 草稿，更新原问题的答复和状态、追加新问题；反馈记录按轮追加。产品改口时保留原答复与变更原因。
- 每轮汇总「已确认 / 仍待确认 / 本轮新增」，给出 PRD 的业务规则、场景、范围和验收调整建议；只在用户要求修改 PRD 时改原文。
- 更新后再次 finalize，旧版自动归档，输出新版链接。内容变化会撤销本轮旧需求和方案凭据及下游确认，保留旧文件；后续须重新收尾需求与方案，M / L 重新确认方案。仍有未定业务项时继续留在 F2；「继续」或已修改 PRD 不代表未回答的问题自动确认。
- 新会话明确继续时，读清单、最新 PRD 和运行 context，从未解决项继续，不重问仍有效的已确认项。

业务项均已回答或由用户明确移出范围后，将清单标为「业务已明确」并 finalize。结合核对后的场景完成 F2 的代码与数据调研，再 save F2 completed、进入 F3。这里不提前生成 requirement.md，也不把业务反馈视为技术约束已确认。

## F3 — 基于业务场景做技术澄清

以清单中的已确认场景（无清单时以已确认需求）和 F2 调研证据为输入，检查：

| 技术方向 | 自己查证 / 需要明确的约束 |
|---|---|
| 现有能力与可行性 | 系统能否支持目标场景，缺口在哪 |
| 接口与兼容 | 现有调用方、旧客户端与协议约束 |
| 数据与一致性 | 字段含义、已有数据、事务、迁移约束 |
| 权限与安全 | 现有鉴权与数据隔离能否满足业务规则 |
| 依赖与运行条件 | 下游能力、配置、性能容量及可验证条件 |

能查证的先查证；只有确实需要用户取舍的技术约束才分轮提问，给出推荐和依据，不把一般实现选择变成确认题。详细设计、改哪些文件和实施步骤留在 F4。

技术调研发现新的业务决定或场景冲突时，回 F2 更新业务清单并等待产品确认；确认后重查受影响的技术事实，再回 F3。已确认且不受影响的场景不重复问。bug 在 B3 内更新清单后继续技术澄清。

业务场景与技术约束都明确后，汇总需求目标、范围、验收标准、已确认决定和必要技术约束。M / L 等用户确认理解一致；已有答复可直接复用，不重复确认。沿用已有运行、复核规模（无需清单时在此判定通道，完整流程 bind、start），用 `artifact.mjs finalize --kind requirement` 收尾 requirement.md 并完成 F3 / B3，再进入 F4。

requirement.md 是最终需求事实来源，引用清单 cite 与版本，只汇总有效场景、决定与约束；清单保留业务往返核对过程，plan.md 保存实现设计。值得长期记住的规则与取舍在交付时作为 DocNexus 沉淀候选。
