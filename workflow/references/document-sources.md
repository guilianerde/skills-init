# 技术方案与上线方案取材

确定需求并创建或恢复文档运行后，在项目根运行：

```bash
node <skills>/workflow/scripts/document-sources.mjs --branch <开发分支> --id <文档运行id>
```

- `dev` 是同一项目、需求和开发分支上最近完成的 `feature` / `bug` 运行。`artifacts` 给出该次运行登记的产物版本、读取路径和引用。最新版已被覆盖时，使用内容匹配的同版本归档；`missing` 中的文件略过，不借用其他轮次的版本。`content_changed: true` 表示当前文件版本相同但收尾后的内容已变化（例如更新了 Wiki 或 DocNexus 元信息），正文先与其他来源核对，无法核实的内容只作为线索。
- `dev: null` 时，按同一需求和分支的需求文档补充背景与验收；上线方案也可读取同范围的交付说明作为线索。快速通道、旧产物和未完成的运行都可继续按 diff 和可选 PRD 生成。上线方案的 `tech` 是同一需求和分支的技术方案候选，显式 `--tech` 优先。
- 用本次 `<main>...<dev>` 的三点 diff 与相关代码核实实现和部署事实。方案、审查、交付说明或旧技术方案与本次改动冲突时，以本次代码为准，在交付摘要指出影响文档结论的差异。设计意图和已确认的业务取舍标明来源，计划中的行为要核实是否落地。
- dev 验证与审查只覆盖原运行的代码、范围和环境，报告时标明来源。代码或基线变化、覆盖范围不一致或无法确认时，将结果视为历史记录，相关场景列为待回归。上线后的验证结果需要上线后实际执行才能填写。
- 交付摘要列出实际引用的文档路径或 cite 与版本，以及影响结论的缺失、差异和待确认项。按模板对应章节取材。
